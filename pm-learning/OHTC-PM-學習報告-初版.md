## 2. 各階段要懂到什麼程度

### A. 系統全貌

- **層級關係**：MES（製造執行系統）下命令給 MCS（物料控制系統），MCS 把搬運命令派給 OHTC（OHT 控制器），OHTC 調度 OHT 車輛；設備端的 load port 透過 E84 PIO 訊號與 OHT 交握。
- **每套系統要知道四件事**：負責什麼、輸入輸出是什麼、窗口是誰、出問題時誰先查。
- **介面標準名詞**：SEMI E82（MCS 與搬運系統介面）、E84（載具交接的 PIO 交握）、E87 / E88（載具與 Stocker 管理）、E5 / E37（SECS-II / HSMS 通訊）。PM 不必會實作，但要聽得懂工程師在爭什麼。
- **OHTL**：我不確定你們公司對 OHTL 的定義，請你在第 6 節補充。
- **懂到什麼程度**：能用一張圖畫出資料流與責任切分，並說出三個常見的跨系統問題與各自的第一個查法。

### B. 開案與前置

- **人員入廠**：護照效期、台胞證、簽證或工作許可、體檢、保險、客戶廠區安全訓練、門禁申請、住宿交通。要做成 checklist，並標註每項的前置天數。
- **硬體採購**：IPC / 伺服器規格（CPU、記憶體、硬碟與 RAID、網卡數量、作業系統、資料庫授權）、交換器、UPS、機櫃、線材、備品。重點不是背規格，而是知道交期與每項規格是誰簽核。
- **懂到什麼程度**：能自己開出一張採購需求單，並說出每項規格的理由。

### C. 設計與圖資

- **CAD 圖到軌道圖資**：節點、區段、分歧與合流、站點與 port、停車區、維修區、速度區間。
- **設備對點**：每個 load port 對應哪個站點、E84 訊號接到哪裡。
- **網路設計**：網段規劃、VLAN、IP 表、MAC 表、車輛無線通訊方式、與客戶網路的介接點。repo 裡 10/27 那份紀錄正是這部分的起點。
- **懂到什麼程度**：圖資或 IP 一改，你能立刻說出要通知誰、重測什麼。

### D. 模擬與測試

- **環境組成**：OHTC 主程式、MCS 模擬器、車輛模擬器、測試用圖資。
- **測試項目**：搬運命令完整流程、異常情境（車輛故障、斷線、路徑阻塞）、多車效能、與 MCS 的介面案例。
- **產出**：測試計畫、測試報告，作為 FAT（出廠驗收）依據。
- **懂到什麼程度**：能看測試報告判斷「可以進廠了嗎」，並說出還缺哪些案例。

### E. 現場導入

- **順序**：施工 → 送電 → 單機動作 → 網路通訊 → 伺服器 / IPC 安裝與軟體部署 → 連線測試 → 與 MCS 整合 → 試運轉 → SAT（現場驗收）。
- **送電**：送電檢查表、安全程序、誰有權下令送電。
- **網路**：通訊確認（ping、port、時間同步、防火牆）、IP / MAC 表到現場逐台核對。
- **伺服器與 IPC**：作業系統、資料庫、OHTC 軟體版本、備份與還原、帳號權限。
- **懂到什麼程度**：早會聽到一個問題，能立刻歸類到哪一層、責任人是誰、預計何時解。

### F. 試運轉與數據

- **資料來源**：OHTC 資料庫、搬運命令紀錄、車輛日誌、警報紀錄、MCS 端紀錄。
- **關鍵指標**：搬運時間、單位時間搬運量、車輛稼動率、警報次數與類型、平均修復時間。
- **分析目的**：找瓶頸、看異常趨勢、算驗收指標達成率。
- **懂到什麼程度**：能自己抓一份週報數據，並講出三個洞察與對應行動。

### 橫向：專案管理

- **日報 / 週報 / 早會**：固定格式、固定四個問題：進度、問題、風險、需要的支援。
- **問題與風險清單**：編號、責任人、期限、狀態，每天更新。
- **溝通升級**：什麼情況要升到主管、什麼情況要升到客戶。
- **變更管理**：範圍、時程、規格變更的流程與簽核。

## 4. 怎麼行動：先學什麼、先做什麼

### 第一個月：把地圖畫出來

- 畫一張系統架構圖與責任切分圖，標上每個窗口的名字。
- 建三張 checklist：入廠人員、硬體採購、送電檢查。
- 把現有專案的問題清單從頭讀一遍，分類成第 1 節的階段。
- 每天早會做筆記，把主管問的問題分類。

### 第二個月：跟完一輪關鍵作業

- 跟一次完整的模擬測試，從測試計畫看到測試報告。
- 跟一次現場送電與通訊確認，自己拿 IP / MAC 表逐台核對。
- 自己抓一次數據做週報。

### 第三個月：自己站上去

- 主持早會，自己維護時程與風險清單。
- 對客戶報告一次進度。
- 回頭看第 2 節的「懂到什麼程度」，逐項打勾。

### 「獨挑大樑」的判斷標準

1. 從開案到驗收走完一輪，不需要人帶。
2. 任何階段被主管或客戶問，一分鐘內講得出現況、問題、下一步、需要的支援。
3. 出問題時能判斷是哪一層、找對人、定出時間。

### 5.2 三種把資料交給我的方式

**方式 A：在你電腦上跑**
在你電腦用 Claude Desktop，或在「專案會議紀錄」資料夾開終端執行 `claude remote-control`。那個 session 可以直接讀桌面檔案；PM 系統若是網頁，也能用瀏覽器看。優點是不用搬資料，也不會把機密放到 GitHub。

**方式 B：放進這個 repo**
把會議紀錄複製到 `meeting-notes/`，PM 系統匯出的 Excel、CSV 或截圖放到 `pm-system/`，然後 commit 並 push。我在雲端就能全部分析。push 之前請確認 repo 是 private，因為會議紀錄通常含客戶名稱。

**方式 C：Google Drive**
上傳到 Google Drive 的一個資料夾，告訴我資料夾名稱。這個 session 有 Google Drive 連接器可以讀取。

### 5.3 我會怎麼分析

**會議紀錄**

1. 盤點：檔案數量、日期範圍、格式、涉及的專案名稱。
2. 結構化：每份紀錄拆成「現場報告事項、主管提問與指示、待辦、問題」四塊。
3. 主管關注分析：統計主管提問的主題與頻率、追問的深度、哪些問題反覆出現。
4. 現場報告分析：現場人員報什麼、用什麼格式、哪些資訊常缺以致被追問。
5. 時間軸：每個專案的事件順序，對照第 1 節的生命週期，找出典型延誤點。

**PM 系統**

1. 把工作項目依第 1 節的階段分類，整理成標準 WBS。
2. 每個工作項目標出前置與後續、責任窗口、典型工期。
3. 跨專案比較：哪些項目每案都有、哪些是特例、常卡在哪。
